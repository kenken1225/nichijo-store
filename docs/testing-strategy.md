# テスト方針と構成（nichijo）

単体・結合・E2E をどう割り当てるか、**このリポジトリ向けのルール**を一枚にまとめています。Vitest 導入後もここを参照して、レビューや新規テストの置き場所を揃えます。

---

## 1. なぜテストを分けるか（テストピラミッドの考え方）

| 層 | 役割 | トレードオフ |
| --- | --- | --- |
| **単体** | 関数・小さなモジュールの入出力を高速に検証 | ブラウザや Shopify 本番には触れない |
| **結合** | 複数モジュールや API Route を**モック付き**でつなげて検証 | 単体より遅い・設定がやや重い |
| **E2E** | ブラウザでユーザーフロー全体を検証 | 遅い・外部・壊れやすい（フレーク）になりやすい |

**方針**: インパクトが大きい流れ（カート・バリアント・チェックアウト導線など）は E2E で**少数**保証し、分岐や整形ロジックは**単体に寄せる**。同じ検証を E2E だけで何度も書かない。

---

## 2. 使うツール（このプロジェクト）

| 種類 | ツール | 用途 |
| --- | --- | --- |
| 単体・軽い結合 | **Vitest** | `src/` 配下の純粋関数、ドメインロジック、（必要なら）コンポーネント |
| E2E | **Playwright** | クリティカルなユーザーシナリオ（既存: `test-playwright/`） |

- **Lint**: ESLint（`npm run lint`）は品質ゲートだが、**振る舞いの回帰検証ではない**。テストレイヤーとは別枠として扱う。

---

## 3. ディレクトリとファイル命名

```
test-playwright/          # E2E（Playwright）*.spec.ts
src/
  lib/
    shopify/
      domain/
        collection-filters.ts
        collection-filters.test.ts   # 単体：同じフォルダに *.test.ts（推奨）
  ...
vitest.config.ts          # Vitest 設定（導入時にルートに配置）
```

**推奨ルール**

- **単体・結合（Vitest）**: テスト対象と**同じディレクトリ**に `*.test.ts` または `*.spec.ts` を置く（インポートパスが短く、探索しやすい）。
- **E2E**: `test-playwright/` に集約。ファイル名は `*.spec.ts`。
- **API Route の結合テスト**: `app/api/...` の近く、または `src/lib/...` のテストから Route 用のヘルパを呼ぶ形にすると整理しやすい（導入後に様子を見て固定する）。

---

## 4. レイヤーごとの「何を書くか」（このコードベースの例）

### 単体（Vitest）向き

- **`src/lib/`** の純粋関数（国・通貨、URL・クエリ整形、コレクション／フィルタのドメインロジックなど）
- **Zod スキーマ**の valid / invalid ケース
- **バグ修正した分岐**の再発防止用の最小ケース

**あえて避ける**: サードパーティ（Shopify SDK 内部）の挙動そのもの、ピクセル単位の見た目。

### 結合（Vitest + モック）向き

- **`app/api/*`**: `fetch` や Storefront クライアントを**スタブ／モック**し、ステータスコードと JSON 形を検証
- **React Context + 子コンポーネント**: 必要なら **React Testing Library** で短いシナリオ（導入は段階的でよい）

### E2E（Playwright）向き

- **カート追加**など、課金・信頼に直結する**ごく少数のスモーク**
- 本番／ステージング／ローカルは **`E2E_BASE_URL`** で切り替え（`.env.e2e.example` 参照）

---

## 5. 優先順位の付け方（どこから手を付けるか）

1. **変更が多い・バグが出やすい純粋ロジック**（例: `src/lib/shopify/domain/`）から単体を足す。
2. **一度壊した箇所**には必ずテストを添える（バグとセットで入れる）。
3. E2E は**本数を増やしすぎない**。増やす前に単体／結合へ降ろせないか検討する。

---

## 6. 実行コマンド

| コマンド | 内容 |
| --- | --- |
| `npm run test` | Vitest（1 回実行、`src/**/*.test.ts`） |
| `npm run test:watch` | Vitest ウォッチモード |
| `npm run test:e2e` | Playwright（既存） |
| `npm run test:e2e:ui` | Playwright UI モード（デバッグ向け） |

CI: Vitest は `.github/workflows/build-check.yml`（`main` の push / PR）。E2E は `.github/workflows/playwright.yml`（定期 + 手動）。

**いつ何を回すかの整理**は [§11](#11-判断基準と実行タイミング面接社内説明用) も参照。

---

## 7. テストのコツ（フレークとメンテ）

- **フレーク**＝同じテストがたまたま成功／失敗を繰り返すこと。放置すると「赤＝信用できない」になる。
  - 固定秒の `sleep` より、**要素・レスポンスの到達を待つ** API（Playwright の locator、Vitest 側は async の `findBy` を優先）。
  - E2E は**テストデータの衝突**（同じ商品・同じユーザー）に注意。環境変数で商品名を切り替えるなど既存パターンを踏襲する。
- **レビューで見ること（短い合意でよい）**
  - バグ修正に**再発防止テスト**があるか、または理由が PR に書いてあるか。
  - 重い E2E で済ませず、下位レイヤーに降りられるか。

---

## 8. 環境変数・秘密情報

- **E2E**: `.env.e2e.example` を参照。`E2E_BASE_URL` / `E2E_STOREFRONT_PASSWORD` / `E2E_FEATURED_PRODUCT_NAME`。
- **単体・結合**: 原則 **モックで完結**。実ネットワークや本番トークンに依存させない。

## 11. 判断基準と実行タイミング（面接・社内説明用）

「何をテストするか」と「いつ自動実行するか」は別の話として説明できると通りやすい。

### 11.1 優先順位の判断基準（何を書くか）

| 判断軸 | この方針での考え方 |
| --- | --- |
| **壊れたときの影響** | カート・価格・在庫・言語・通貨・認証・チェックアウト導線などは優先度が高い。 |
| **変更の頻度** | よく触る `src/lib` や `domain`・フィルタ周りは、単体を足すと手戻りが減りやすい。 |
| **レイヤーの割り当て** | 同じ検証を E2E で何度も書かず、**分岐・計算は単体／結合**、**ユーザー価値の一本道は E2E で少数**に寄せる。 |
| **再発防止** | バグ修正には**その分岐のテスト**を添えるか、テストが難しい理由を PR に書く。 |

**面接で短く言うなら**: 「リスクと変更頻度で優先順位を付け、速いテストで広く、E2E は少数のスモークでコストと信頼のバランスを取る」。

### 11.2 実行タイミング（いつ回すか）

| 種別 | 想定される実行タイミング |
| --- | --- |
| **単体・結合（Vitest）** | ローカルで随時。**CI は PR ごとが理想**；負荷や導入段階なら `main` マージ時だけなどに段階導入してよい。 |
| **E2E（Playwright）** | 既存ワークフローどおり **定期実行＋手動**。環境・データ依存が強いので、**全 PR で必須にしすぎない**選択もありうる。 |
| **Lint** | `npm run lint`。振る舞いの回帰ではないが、**別ゲート**として併用する。 |

---

## 12. この方針で工夫した点（面接・社内説明用）

実装量より「**判断を共有できる形にした**」ことを工夫として語れる。

1. **ツール導入より先に、方針をドキュメント化した**  
   ピラミッド・置き場・命名・優先順位を先に固定し、あとから Vitest や CI を足してもブレにくくした。

2. **このリポジトリ固有のパス・ツールに紐づけた**  
   抽象論ではなく、`src/lib`・`domain`・`test-playwright`・`.env.e2e` など**実在する構成**で例を書いた。

3. **「やらないこと」を明示した**  
   サードパーティ内部の検証、見た目のピクセル単位、E2E の乱造、本番トークンに依存した単体などを避ける、と書いて**レビュー時の判断材料**にした。

4. **フレークとレビュー観点まで含めた**  
   テストが増えたあと詰まりやすい**信頼性**と、PR で最低限見る項目を短く盛り込んだ。

5. **導入チェックリストを置いた**  
   「ドキュメントだけ残って実行されない」状態を避けるため、スクリプト・設定・最初の 1 本・CI の検討を箇条書きにした。

**30 秒程度の例文（自己紹介・プロジェクト説明用）**  
「テストはリスクとレイヤーで優先順位を付け、E2E は少数のスモーク、ロジックは単体に寄せる方針にしました。戦略を MD にまとめたうえで Vitest を入れ、コレクションフィルタのドメインロジックを単体テストし、Build Check の CI で毎 PR 実行しています。」

---

## 13. 面接で誠実に言っておくと強いこと

- **完了していることの例**: 方針ドキュメント、Vitest（`collection-filters` の単体）、E2E（Playwright 既存）、PR 時の `build-check` に unit 実行。
- **まだ薄い／次の一歩の例**: 結合テスト（API Route のモック）、コンポーネントテスト、単体のカバレッジ拡大——など、**言葉を大きくしすぎない**ために不足を一言添える。
